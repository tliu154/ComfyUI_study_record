# 实操 07：尺寸、显存与 VAE 解码

> 对应章节：[第 7 章 潜空间](../docs/ch07_latent.md) ｜ 预计耗时：25 分钟
> 状态：`[已完成]`

## 目标

通过改尺寸观察显存/耗时变化，理解「潜伏空间压缩」的实际影响；并再次验证 VAE Decode 的作用。

## 前提

- [ ] [`ch03_task.md`](../../00_getting_started/tasks/ch03_task.md) 工作流已保存
- [ ] 任务管理器性能页打开，可看 GPU 显存占用（显存监控）

## 步骤

1. **加载 ch03 工作流**，固定 seed。

2. **尺寸对照**（其余不变）：
   - 512×512 → Queue Prompt，记录显存峰值与耗时（记为 A）
   - 768×768 → 同样记录（记为 B）
   - 1024×1024 → 记录（记为 C）；若 OOM 报错就停下，说明到了你显存的边界
   → 观察：尺寸越大，显存和耗时越高（近似按面积增长）

3. **验证 VAE Decode**：把 `VAE Decode` 的 `vae` 输入断开，Queue Prompt，
   观察出图颜色异常（发灰/发绿）——印证它是「显影」关键；接回还原。

4. **观察 latent 尺寸**：悬停 `Empty Latent Image → KSampler` 的橙线，确认类型 LATENT。
   想想：512×512 的图压缩成 latent 后大约是 64×64（1/8）——这就是它省算力的原因。

## 验收标准

- [ ] 记录了 3 个尺寸的显存/耗时，看出「尺寸越大越吃资源」
- [ ] 断开 VAE 后颜色异常，接回恢复
- [ ] 确认橙线是 LATENT

## 改一改会怎样（小实验）

| 改动 | 预期现象 | 为什么 |
|---|---|---|
| 尺寸拉到远超模型训练值（如 1536）| 可能出畸形/重复 | 尺寸要匹配模型训练分辨率，见 ch07 7.4 |
| batch_size 从 1 调到 4 | 显存明显上升 | batch 线性增加显存，见 ch12 |

## 常见问题

- 调大尺寸 OOM → 降尺寸或用低显存模式，见 [ch26](../../06_ecosystem/docs/ch26_performance.md)
- 出图畸形 → 尺寸偏离模型训练值太多，回到 512 系
- 其它 → [附录 C 故障排查](../../90_appendix/docs/appC_troubleshooting.md)

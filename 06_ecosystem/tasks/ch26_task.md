# 实操 26：记录显存与耗时，演练降本顺序

> 对应章节：[第 26 章 性能与显存优化](../docs/ch26_performance.md) ｜ 预计耗时：40 分钟
> 状态：`[已完成]`

## 目标

给自己的机器建立一份「显存 / 耗时」基线记录，
并通过一次「一次只改一个变量」的小实验，验证降尺寸/降精度对显存和速度的影响。
**如果机器配置好、从没遇到 OOM，本任务仍值得做——建立基线，将来出问题有对照。**

## 前提

- [ ] 会搭并跑通 SD1.5 文生图（ch03）
- [ ] 能看显存占用：任务管理器 GPU 页 / `nvidia-smi`（N 卡）/ ComfyUI 日志
- [ ] 前置概念：显存花在哪，见 [ch26 26.1](../docs/ch26_performance.md#c26-01)

## 步骤

1. **建立基线**：用固定提示词、固定 seed、SD1.5 模型、`steps=20`、512×512 出一张图。
   记录：显存峰值、耗时、是否成功。填入下面记录表的「基线」列。

2. **只改尺寸**：保持其它参数不变，只把尺寸改成 768×768（或 1024×1024），再出一张。
   记录显存/耗时。观察变化，见 [26.1](../docs/ch26_performance.md#c26-01)。

3. **只改 batch**：尺寸改回 512，`batch_size` 从 1 改到 2（或 4），再出一次。
   记录显存/耗时。

4. **（有低精度模型则做）换精度**：若你有 fp8 / 量化版模型，换它出一张，记录显存/耗时与画质变化，见 [26.3](../docs/ch26_performance.md#c26-03)。
   没有可跳过，记「无」。

5. **（可选）试低显存模式**：用 `--lowvram` 启动（见 [26.2](../docs/ch26_performance.md#c26-02)），
   重复基线那次，对比速度是否变慢、显存是否更宽松。

6. **（若遇到 OOM）演练降本顺序**：故意开大尺寸（如 1536）触发 OOM，
   然后按 26.4 的顺序逐项降：尺寸 → batch → 精度 → lowvram，直到能跑，记下哪一项起了决定性作用。

## 验收标准

- [ ] 记录表至少填了基线 + 2 组单变量实验的显存/耗时
- [ ] 能说出「哪个变量对显存影响最大」（通常是尺寸或精度）
- [ ] 理解了「一次只改一个变量」便于归因

## 改一改会怎样（小实验）

| 改动 | 预期现象 | 为什么 |
|---|---|---|
| 尺寸 512→1024 | 显存约翻几倍、变慢 | latent 面积按宽×高增长，见 ch26 26.1 |
| batch_size 1→4 | 显存近似线性增加 | 一次多张，见 ch26 26.1 |
| 换 fp8/量化模型 | 显存降、可能略提速、画质略降 | 精度降低，见 ch26 26.3 |
| 开 --lowvram | 显存更宽松但变慢 | 主动卸载换空间，见 ch26 26.2 |

## 常见问题

- 看不清显存峰值 → 用 `nvidia-smi -l 1` 每秒刷新，或任务管理器 GPU 页「专用 GPU 内存」
- 换了精度画质差太多 → 说明该模型量化损失偏大，换回高精度或换别的量化版
- 开 lowvram 反而更慢 → 正常，它本就是拿速度换显存，见 [26.2](../docs/ch26_performance.md#c26-02)
- 其它 → [附录 C 故障排查](../../90_appendix/docs/appC_troubleshooting.md)
